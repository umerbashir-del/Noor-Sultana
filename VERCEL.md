# Noor on Vercel

The root `vercel.json` builds the existing prototype interface into `public/` and deploys a small request-based API. This Vercel preview supports text chat with Claude, current JFK/Tokyo weather, the sample arrival forecast while it remains in the future, and the seven draft passenger guidance pages.

The Vercel app needs two **Secret** environment variables in both Preview and Production: `NOOR_SESSION_SECRET` (32 random bytes encoded as 64 hex characters) and `ANTHROPIC_API_KEY`. An optional `ANTHROPIC_MODEL` selects the Claude model. Configure secrets in Vercel; never commit them. Redeploy after changing environment variables.

Server-backed sessions are required. Configure `SUPABASE_URL` and `SUPABASE_SECRET_KEY` on the Vercel server in both Preview and Production, then apply `supabase/migrations/20261012_noor_demo_sessions.sql` to the Noor Supabase project. Use a dedicated Supabase secret key in Vercel; never expose it in client code or source control. Redeploy after changing environment variables.

The browser keeps an encrypted, HttpOnly session ID and a separate encrypted anonymous visitor ID. Supabase owns the messages, session memory and counters, enforcing 15 minutes idle, two hours total and, after the session-allowance migration below, 100 questions per conversation. End conversation deletes the session but never its usage records. Missing storage fails closed; the cookie-only hosted fallback is no longer accepted. Apply `supabase/migrations/20261012_noor_demo_retention.sql` to prune expired sessions. Anonymous visitor cookies provide continuity rather than strong identity: clearing cookies creates a new visitor, so the global spending cap remains essential.

Before deploying the new hosted budget code, apply `supabase/migrations/20261011_noor_foundation.sql` if it has not already been applied, followed by `supabase/migrations/20261018_noor_hosted_budget.sql` after the existing session migration. The new migration is additive: it does not reset or delete existing usage. Pre-migration sessions without a visitor association must start a new conversation. Deploy the matching server code after applying the migration. Missing migrations or unavailable budget storage block model requests.

Every Claude model round, including tool continuations and repairs, reserves tokens atomically in Supabase before the provider request. Actual usage settles the reservation; missing usage and uncertain provider outcomes keep the reserved amount. UTC-day totals span conversations and server instances, using all existing Claude records in `noor_usage_events`. Default hosted limits are 100 model calls and 30,000 tokens per visitor per UTC day, and 500 calls and 300,000 tokens overall. Override them using server environment variables `NOOR_DAILY_CLAUDE_VISITOR_REQUESTS`, `NOOR_DAILY_CLAUDE_VISITOR_TOKENS`, `NOOR_DAILY_CLAUDE_GLOBAL_REQUESTS` and `NOOR_DAILY_CLAUDE_GLOBAL_TOKENS`. Client request fields cannot change these limits. Local SQLite usage remains separate and is not modified by the hosted migration. Keep an Anthropic account spending cap as another safeguard.

For the October 19, 2026 New York demo only, apply `supabase/migrations/20261019_noor_hosted_demo_day_allowance.sql` and deploy the matching hosted API code. Through midnight New York time, the production passenger and crew model limits and hosted passenger voice/question limits are lifted while all usage remains recorded. The normal application limits resume automatically at `2026-10-20T04:00:00Z`; the local Noor server and Vercel preview are unaffected. Anthropic and Replicate account limits still apply.

For microphone questions, Chrome and Firefox prefer MediaRecorder and send audio to `/api/transcribe` when hosted transcription is available, using the existing server-side Replicate token and pinned Whisper model. This avoids relying on Chrome’s separate browser speech-recognition service. Browsers with Speech Recognition use it only when hosted recording is unavailable. The capability check finishes before Talk is enabled; a failed attempt never starts another recording automatically. The passenger reviews or edits the transcript before Send; transcription never automatically sends a chat message. The UI discloses the browser/Replicate processing path. Missing transcription configuration leaves typed chat and Stop available. Local transcription still uses the faster-whisper worker.

Hosted ASR requires no new database migration: it uses the existing transactional paid-model ledger. Each recording reserves 3,000 accounting units, retains them on failures/uncertain outcomes, and records actual tokens as null; these units are not measured Whisper tokens. ASR shares the legacy `NOOR_DAILY_CLAUDE_*` request/allowance totals and the same configured hosted spending policy. Normal defaults are 100 calls/30,000 units per visitor and 500 calls/300,000 units globally; existing chat usage counts too. The already-approved October 19 production presentation allowance also applies to ASR, so earlier chat usage does not block Talk during that exception. Normal limits resume automatically October 20 at midnight New York time. No new unlimited setting or exception period was added. The browser stops recording after 30 seconds. The server caps uploads at 900 KB, bounds upload reads and the full processing path, and cancels upstream predictions on Stop or timeout. The ASR function permits 60 seconds including bounded cleanup.

Live2D is delivered from the pinned `prototype/live2d/noor-v6/` application bundle into `public/live2d/noor-v6/`, including Core, Framework, shaders, model/texture and notices. The hosted renderer has no localhost-only gate. The flight page CSP permits WebAssembly compilation with `wasm-unsafe-eval`, without broad `unsafe-eval`. A missing or altered required asset fails the build rather than silently shipping a static-only site. Private editable rigs and the raw SDK remain excluded.

For spoken replies, apply `supabase/migrations/20261012_noor_demo_voice.sql` and `supabase/migrations/20261012_noor_demo_voice_429.sql` before deploying the corresponding server code, then set `REPLICATE_API_TOKEN` as a Vercel Secret in Preview and Production. After Replicate billing is ready, set `NOOR_VOICE_ENABLED=true` in the desired environment and redeploy. The server sends the last saved Noor reply and the Hope reference clip to Replicate's official `resemble-ai/chatterbox-turbo` model. The token stays on the server. Until voice is enabled, the voice control says Chatterbox is not connected and text chat still works. Only the most recent saved Noor reply can be spoken, with at most 50 voice requests per conversation and 20,000 characters per UTC day across the demo. A provider 429 on prediction creation returns a clear wait message and releases that request's demo allowance; other failed or canceled provider calls can still count, so set a separate Replicate account spending limit. Replicate receives the reply text and reference audio, and the generated audio is fetched through Noor's server. Voice predictions now return an ID promptly, so Stop can cancel an active Replicate prediction while it is still generating. Noor pauses briefly before starting a new voice request after an interruption; the usage reservation for the canceled request remains counted.

Passenger shortcuts include the fictional boarding time, draft baggage guidance, weather availability, and the fixed arrival note. Current weather questions can name a city, optionally with a state or country. Noor resolves it through Open-Meteo geocoding and shows the resolved place, source, and update time. Ambiguous place names need clarification. The fictional arrival forecast remains limited to Tokyo.

The Vercel preview still cannot schedule email. Vercel functions do not keep the local Python workers or SQLite email scheduler running between requests. Do not present the fixed email note as sent or scheduled.

Run `npm run build` and `npm run test:vercel` from the repository root to check the Vercel build and API flow locally. The generated `public/` directory is ignored by Git.

Hosted demo crew requests and passenger reminders use the existing confirmation forms. Apply `supabase/migrations/20261018062000_noor_hosted_actions.sql` before deploying this support. Supabase stores action drafts and confirmed items in the current session, using versioned writes to prevent overwrites. Only the server role can access these functions. Ended or expired conversations cannot read or change their actions. Review tokens expire after five minutes (or the reminder due time), and repeated confirmations return the same saved item. Each session permits up to ten crew requests and ten reminders. These actions do not call Claude or change its usage ledger or caps.

Crew submissions are simulated records, not dispatches or notifications to actual crew. Reminders are manual in-page alerts: keep the page and conversation active; idle and absolute session expiry still apply. There is no email, SMS, push, background scheduling guarantee, or adjustment for flight changes. Refreshing the reminder list checks current server time; hosted function restarts do not erase session records.

The demo crew dashboard is `/crew-dashboard.html`. Before deploying, apply `supabase/migrations/20261018065000_noor_crew_dashboard.sql` and configure `NOOR_CREW_DASHBOARD_KEY` as a random server-side secret of at least 32 characters. Never put the code in frontend assets, URLs, or source control. Crew sign-in grants a separate signed, HttpOnly, Secure, SameSite cookie valid for two hours; rotating the access code invalidates previous cookies. This shared demo code is not production staff identity management.

Only confirmed requests from active conversations appear, up to 200 entries. Crew can acknowledge, start, and complete requests in order. Updates lock the session row and increment its action version, so concurrent passenger changes cannot overwrite crew progress. Passengers see fresh status in their request panel approximately every ten seconds while the conversation is active. Completed requests cannot be cancelled by a passenger. No Claude or voice calls are needed for queue updates.

Crew Noor can also answer queue questions and draft handovers with the existing server-side `ANTHROPIC_API_KEY`. Before deploying crew Claude, apply `supabase/migrations/20261018072000_noor_crew_claude_budget.sql` and run `scripts/check-crew-claude-budget.sql` inside a transaction that is rolled back. Crew sign-in creates a separate two-hour server-backed crew session. Missing storage or budget functions fail closed before a Claude call; existing passenger usage records and limits are not reset. The crew budget defaults to 80 model rounds and 60,000 tokens per UTC day, 40 model rounds per sign-in, and six model rounds per minute per sign-in. A typical tool-backed question takes two rounds. Every crew round also counts against the existing shared overall Claude request and token caps. `NOOR_DAILY_CLAUDE_CREW_REQUESTS`, `NOOR_DAILY_CLAUDE_CREW_TOKENS`, `NOOR_DAILY_CLAUDE_CREW_SESSION_REQUESTS`, and `NOOR_DAILY_CLAUDE_CREW_MINUTE_REQUESTS` can set lower or higher crew-only bounds without changing the shared overall cap.

The dashboard has a separate read-only fictional sample queue for presentation. Sample requests never appear in passenger sessions and cannot be updated. Claude receives only bounded read-only crew tools; passenger-written request details are untrusted tool data. The server renders factual answers from tool evidence and exposes only a review proposal for an allowed status transition. The existing crew confirmation endpoint performs the actual version-checked update. Crew handovers and passenger wording are drafts and are not sent. Redacted crew traces contain tool names, outcomes, and usage metadata, never questions, request text, or credentials.

Apply `supabase/migrations/20261020_noor_session_allowances.sql` after the October 19 allowance migration to raise the normal conversation limits to 100 questions and 50 voice attempts. Run `scripts/check-session-allowances.sql` using a database administrator connection; it checks both boundaries inside a rolled-back transaction without provider calls. The temporary October 19 exception still ends at its original deadline. This does not promise 100 paid answers: tool rounds and ASR share the visitor’s 100-call/30,000-unit daily allowance, global limits remain 500 calls/300,000 units, and voice retains its shared 20,000-character daily cap. Explicit server environment overrides still take precedence. Session expiry, recording limits and provider limits remain unchanged.
